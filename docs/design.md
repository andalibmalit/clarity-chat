# Design

Why Clarity works the way it does: each choice, what it costs, and what is out of scope. For what each key and command does, see [Reference](reference.md); for how to use them, see [Guides](guides.md).

## Principles

- **What you see is exactly what the model got, and every completed call can be replayed.**
- **No silent fallbacks.** If something can't be done exactly as configured, Clarity stops with a clear error. Two cases are flagged instead, on the record and on screen: a check that fails after a call, and a setting the Transformers backend can't apply.
- **What Clarity trusts.** It acts on these as written: its own code and locked dependencies, your llama.cpp build, the files it ships, your `local/` folder, and what you type or pass on the command line. Everything else is untrusted: logs and exports (yours may be hand-edited, or someone else's), profiles and prompt files from someone else, downloaded model files and their chat templates, everything llama-server sends back and, from v0.3.0, every request from the browser. Untrusted input may be refused, but it must never reach a command line, a file outside the project folder or a network setting unchecked. So logged flags go through the same checks as `server.toml`'s, and a profile's prompt files must be inside the project folder.
- **Clarity gets out of the way.** Being exact must not make common experiments awkward. Where a strict rule gets in the way, the answer is a small, explicit shortcut that is itself logged, such as `use_recommended = true`, not more ceremony.

## The prompt

**The client owns the prompt, down to the token IDs.** It renders the prompt and tokenizes it with the model's Hugging Face tokenizer at a pinned commit, then sends token IDs. No server applies a template or tokenizes.
- Cost: the tokenizer and template files must be in the Hugging Face cache, and `transformers` is a dependency (without torch).
- Check: after each call, the server's own decoding of the IDs must equal the prompt text, which shows that the tokenizer and the GGUF agree.

**BOS is decided per mode and logged.** Text mode follows `add_bos_token` in `tokenizer_config.json`, cross-checked by probing the tokenizer; if they disagree, the profile won't load. Chat mode never adds BOS, because the chat template decides.

**Chat templates come from a pinned repo and are logged by hash.** Each call logs the template's repo, commit, arguments and sha256, plus the `transformers`, `tokenizers` and `jinja2` versions, because rendering depends on all of them.
- A template can write today's date: Transformers gives templates `strftime_now`, which formats the machine's current local time. Some templates, such as SmolLM3's and Apertus's, call it. Then the same messages can make a different prompt on another day. Clarity warns at a conversation's start and on resume, and doesn't pin the date: each call logs the prompt it sent, and replay sends the logged token IDs. No shipped model's template calls it.

**Text that looks like a control token is a control token.** If a message or prompt file contains, say, `<|im_end|>`, the tokenizer reads it as that token, as Hugging Face does everywhere. Clarity keeps this standard behaviour so both backends get the same IDs, and flags and warns about such calls instead.
- Cost: there is no way to send such text as plain text.

**Each call records where each message sits in its prompt.** A message's tokens differ from call to call: OLMo 3 ends only the last reply with `<|endoftext|>`, Gemma 4 ends the prompt with an empty thinking block when thinking is off and strips thinking from earlier replies, and Qwen rewrites earlier reasoning. So the spans come from each call as it was rendered, never from rendering the conversation again later. To find them, Clarity renders the call a second time with each message replaced by a unique placeholder, which shows the template's own text around each message, then puts the messages back and checks that the result equals the real prompt exactly. A template that trims a message's edge whitespace is matched by trying that message stripped, and the span says `trimmed`. A template that rewrites, drops or repeats a message gets no spans for that call, with the reason, never a guess; a call never fails over its spans.
- Tokens come from the fast tokenizer's character offsets, checked to give the call's own IDs and to cover the text without gaps. A token that crosses an edge belongs to the span it starts in, which says `edge_token`. In text mode, `User: ` is the profile's text, so a tokenizer that joins the space to the first word gives that token to the profile, not the message.
- Checked over 26 saved chat templates: plain messages give spans on all 26; with edge whitespace, 25; with a `<think>` block in a reply, 21 (the Qwen3.5 and 3.6 family and Nemotron rewrite it).
- Cost: a second template render and a second tokenization per call.

**What you see of a prompt can't change your screen.** A prompt holds whatever text was sent, which can include control characters: an escape sequence can recolour or rewrite the terminal, and a text-direction control such as U+202E can reorder text on screen. The terminal's `/prompt` shows each control character but newline and tab, and each text-direction control, as ⟨U+001B⟩, the notation the web page uses for text-direction controls. The text sent and logged is unchanged, and so are `/prompt repr`, which shows each line as a Python string, and `--json`, whose JSON escapes them.

**Line endings are part of the prompt.** Prompt files are read byte for byte, and `.gitattributes` stops git from converting line endings in `prompts/`, `profiles/` and the test fixtures, so a Windows checkout sends the same bytes.

**A model's end token comes from its own files, not from assumptions.** OLMo 3's template closes the last assistant message with `<|endoftext|>`, not `<|im_end|>`, and the model does the same. Both are end tokens in OLMo 3 Instruct's `generation_config.json`, and llama.cpp stops on either.
- The two backends can stop on different tokens. Transformers stops on the IDs in `generation_config.json` (or the tokenizer's end token, if the file lists none). llama.cpp stops on the end token in the GGUF and also on tokens it recognizes by name, such as `<|im_end|>`, `<|endoftext|>` and some fill-in-the-middle tokens (`vendor/llama.cpp/src/llama-vocab.cpp`). For SmolLM2 that is {0, 2, 4} on llama.cpp (4 is `<reponame>`) against {2} on Transformers; for OLMo 3 base, {100257, 100265} against {100257}. Clarity keeps each backend's own set and doesn't merge them, because merging would change what one backend does. Instead each call's end tokens are a fact (`end_tokens`) that replay, resume and the export check compare, so a difference is shown.

## Settings

**Every sampling value is sent, every time.** Each setting comes from the profile, then from the model's recommended values if the profile opts in, then from `defaults.toml`, whose values turn every sampler off. Every other field llama-server reports gets a fixed neutral value.

After each call, Clarity checks that the server echoed what was sent and reported no field Clarity doesn't know.
- Why: llama-server's defaults aren't neutral, and since the converter copies `generation_config.json` into the GGUF, they can differ per model.
- Cost: the table of neutral values is tied to the pinned llama.cpp commit. An upgrade that adds a sampler fails the check until the table is updated.
- A setting acts only if its sampler is in `samplers`, so a non-neutral setting whose sampler is missing is an error when the profile loads, not a value that silently does nothing.

**The model's recommended settings are opt-in.** With the shared neutral defaults, two models are compared under the same settings unless you choose otherwise. `use_recommended = true` is the one-line way to choose otherwise, and its values are logged with origin `model`.

**Seeds are always concrete, and the default is 42.** With a fixed default, on the same machine and build, the same message with the same history and settings gets the same reply, so a difference between two replies comes from what you changed. `seed = "random"` makes Clarity draw a seed and log it, because llama-server doesn't report a seed it picks itself, and that call couldn't be replayed.

## The server

**Clarity starts its own llama-server.** Every output-affecting flag of the chat server is set in `server.toml` (meaning search's embedder has its own; [Meaning search](#meaning-search)), nothing is left on `auto`, `server.toml` accepts only a fixed list of flags, and the environment variables and config files llama.cpp would read are removed or refused. After startup, Clarity checks `/props` to confirm that the server it started has the expected model and context size, and that its build is the pinned commit; a build from another commit is an error. After each call, it checks that the process is still running. Nothing can change a running server's model or context: `server.toml` allows no flag that would, and the per-start key keeps other programs out.
- Cost: one chat model at a time. Switching to a profile with another model restarts the server.
- The server never parses the model's chat template (`no-jinja`). Clarity doesn't use it, and OLMo 3's fails to parse in llama.cpp, which would stop the server from starting.
- With GPU layers requested, a model that lands on the CPU is an error. Clarity reads where the weights went from llama.cpp's startup output, which reports it only at `log-verbosity` 4.

**Each server start gets a new random key.** llama-server answers any program that can reach its port, including a web page open in your browser: by default its CORS headers let any site read the replies. Clarity passes a new key in the server's environment at each start (`LLAMA_API_KEY`), sends it with every request, and turns off the `/slots` endpoint and the built-in web UI, which would show prompts or stay public. Only `/health` answers without the key.
- The key is never logged. At `log-verbosity` 4, llama-server prints its last four characters; Clarity replaces that line in the startup output and the server log.
- Cost: the key is in the server process's environment, which other programs running as you can read. The key keeps out web pages, not your own programs.

**The context size is per profile.** A long document needs a large context, and a large context takes memory a short chat doesn't need. So a profile can set `ctx_size`; the rest use `server.toml`'s `ctx-size`. The size goes into the server's flags, so argv, the `/props` check and the log agree, and each conversation logs the size and its origin; each call logs `n_ctx`. `/set ctx_size` changes it for one chat, so hitting the limit doesn't need a new profile.
- Cost: switching between profiles of different sizes restarts llama-server, which reloads the model.
- Replay runs a call at its logged size, so the size is never a hidden difference between a call and its replay. In a chat at another size, `/replay` is refused and names the size to set. This is a rule about conditions, not a measured difference: on SmolLM2, 4,096 and 8,192 gave the same tokens in 6 of 6 seeded requests.
- The chat's size changes only after the new start works. A refused size starts the old one again, so a call never runs at a size the chat doesn't show. `/set ctx_size` with no value goes back to the chat's base: the profile's size, or a resumed chat's logged one.
- llama-server quietly caps a size above the model's training context; Clarity refuses it instead, naming the limit.
- On a Mac, Clarity refuses a size whose memory doesn't fit. After llama-server starts, Clarity adds up what it put on the GPU (model, context cache, compute buffers) from its startup log, and compares that with Metal's `recommendedMaxWorkingSetSize`, which Apple describes as an approximation of how much memory the GPU can allocate without affecting its performance. Other apps' memory isn't counted, so the check catches a size that can't fit, not one that a busy machine can't fit right now. Metal's figure counts only the process that asks, so it doesn't see Clarity's other server either: when a chat that searches by meaning runs the chat server and the embedder, whichever starts second adds the running one's logged total to its own. If the two don't fit, that start is refused with both figures; the ways out are a smaller chat model, a lower `ctx_size` or `search_method = "words"`, since the embedder's 8,192-token context is fixed. The Transformers backend has no memory check. Measured, not modelled: on OLMo 3 7B the context cache took 2,752 MiB at 8,192 tokens and 5,824 MiB at 32,768, and the compute buffers 237 and 645 MiB with flash attention (609 and 2,193 MiB without). Other GPUs log the figures only, until the Linux release.

**The model file's banned tokens are recorded.** A GGUF file can list token IDs to ban from every reply (`tokenizer.ggml.suppress_tokens`, which llama.cpp's converters write for some models, such as Gemma 4 Unified (from `generation_config.json`) and MiniMax (token IDs with zero embeddings)). llama-server adds minus infinity to each banned token's logit, beside the request's own logit bias, so no request can lift the ban, and `generation_settings` doesn't show it. It drops IDs outside the vocabulary, which can't be in a reply anyway. Clarity reads the list from llama-server's startup log, where llama.cpp prints each of the file's keys at `log-verbosity` 4, and records it in `server_start` (`[]` for none). The log must hold as many keys as llama.cpp says it dumps, so a log cut short is refused rather than read as no ban. On a file with a ban, each call's `backend_settings` lists it with origin `model file`, `/settings` shows it, and the `suppress_tokens` check confirms that no banned ID is in the reply.
- Clarity reads the log rather than the file: it already captures the log, so there's no file parser and no new input.
- llama.cpp prints a key's value cut to 40 characters, brackets and separators included. A list longer than that, or a log Clarity can't read the key from, refuses the start; this version can't run such a file. A dump with no key line at all is refused too, so `[]` always means the file has no ban.
- Every line of the startup output is searched, and every line naming the key counted; two lines refuse the start. Text from the file can't hide the real key line, since llama.cpp prints each key on its own line and refuses a file with a duplicate key. The risk left: text from the file holding a newline, such as a key's name or the model's name, can print a fake key line. With the real key present that makes two lines, which is refused. Without it, Clarity would log a ban that isn't applied, and the check flags a reply that holds a "banned" token.
- Logs before v0.4.0 don't record the ban, which llama-server applied all the same.
- The Transformers backend doesn't apply the file's ban (it loads the source weights, not the GGUF), and sends `suppress_tokens = None`, with origin `backend`. For such a model, the two backends sample from different distributions; each one's settings show it.

**A cancel works from any thread, and never adds an empty reply.** Whatever starts a call, such as the web page or a script, makes a cancel signal for that call alone, so a late cancel can't stop the next call, and one sent while the prompt is still being built stops the call before anything is sent. The llama.cpp backend checks it between stream lines, and Clarity asks llama-server for a ping each second while it reads the prompt (`sse_ping_interval`; the server's default is 30 s), so the call returns within about a second even then. Closing the stream tells llama-server to stop, which it does once it finishes the piece of the prompt it's working on (`batch-size` tokens). Measured on OLMo 3 7B on an M2 Max: a cancel half a second into a 6,000-token prompt freed the server after 4.3 s; the whole prompt takes 14 s. So a cancel never needs a server restart.
- A cancel before the first token is logged like a failed call, with `cancelled_during: "prompt"`, and your message is offered back. A reply with no text would be a turn nobody wrote.
- Cost: the Transformers backend checks only as each token arrives, so a cancel during its prompt pass takes effect at the first token.

**No prompt cache, no context shift.** A cached prefix can change results, and context shift drops tokens without saying so.
- Cost: every call processes its whole prompt, which is slower in long conversations.

**The context guard allows a call only if prompt + `max_tokens` < context.** At exactly prompt + `max_tokens` = context, llama-server returns every token but marks the reply truncated, so the guard refuses that case (checked live).

## Models and files

**Models are pinned and converted locally.** `models.toml` names a repo and a full commit hash. `fetch` converts with the llama.cpp checkout's own converter, in its own environment, and records everything it resolved in `local/models.lock`.
- The converter's environment is `models/.converter`: a fresh venv on a Python 3.13 that uv installed itself (`uv venv --managed-python`), with nothing from Clarity's environment, folder or uv's config files, and the packages `src/clarity_chat/converter-requirements.txt` pins, installed with `uv pip install --require-hashes --no-build`, so a file whose sha256 doesn't match is refused. Both commands run the uv that runs Clarity (uv sets `UV` to itself), since the install command's `PATH` doesn't hold `~/.local/bin`, where uv's installer puts uv. `--no-build` installs wheels only: an sdist's build dependencies would come from the index unhashed, and its build backend would run. uv's environment variables still apply, except `UV_PYTHON_PREFERENCE`, which `--managed-python` replaces (uv refuses the two together). So an index they name (`UV_DEFAULT_INDEX`, say) is used; the hashes, with `--no-build`, cover every file it serves. Clarity makes the environment before the first conversion, says so first, and makes it again when the requirements file or the commands that make it change, or when its Python is gone (it links to the Python uv chose, which can be removed); a marker inside it holds the sha256 of both, written only after the install succeeds. `uv run --with-requirements`, which made the environment before, checks no hashes. The file ships beside the converter's shim rather than in the folder fetch writes to, so a scratch folder converts as Clarity's own does.
- The pins are the versions bge-m3's conversion recorded, from PyPI, with the hashes of every file PyPI has for them. llama.cpp's own requirements give ranges, not hashes, and admit sentencepiece 0.2.3, whose `model_pb2` needs protobuf 5.26 or later while the same requirements cap protobuf below 5: bge-m3's SentencePiece vocabulary failed to load. The file pins 0.2.2, which imports with protobuf 4. A new llama.cpp pin can need new requirements, and a live test fails when a pin falls outside the ranges llama.cpp's files give at its pinned commit. The maintainer then compiles the file from those files' requirement lines, without their `--extra-index-url` line (the conversions ran with PyPI's torch), plus `sentencepiece==0.2.2`, with `uv pip compile --no-config --default-index https://pypi.org/simple --universal --python-version 3.13 --generate-hashes`; the file's header has the whole command.
- Every fetch writes `local/models.lock`, which git ignores, so fetching never changes a tracked file: a call logs `client.dirty: true` only for a real edit. An entry there wins over the shipped `models.lock`'s entry of the same name. The cost is that a user's entry stays in force until a fetch replaces it; a pin changed in `models.toml` makes it refuse, with the fetch hint.
- The shipped `models.lock` is the reference: the maintainer fetches a model, copies its entry with `scripts/refresh_lock.py`, and commits it, and CI verifies its own fetch against that entry. Lock paths are relative to the repo or written as `~/...`, so an entry carries no user name when it's committed.
- The full sha256 is computed at fetch. A server start checks only size and modification time, which is fast; `clarity verify` re-hashes on demand.
- A copy or `touch` changes a file's time and not its bytes, and a refusal that sends you to a terminal is no help on the page. So a new chat, a resume and the embedder's start hash a GGUF whose size matches its lock entry and whose time doesn't. If the bytes match, they record the new time in `local/models.lock`, say so in one line and go on; if not, they refuse with the fetch hint, as they do at once for another size. A re-hash is the stronger check, so this isn't a fallback. Replay and a batch run keep the refusal, since neither should write the lock partway. The profile listing and setup's "fetched" check the size only and never hash or write: listing every profile mustn't take a minute per model, or change a file.
- A running server is kept for the next profile only if its file is the same: same path, inode, size and modification time. `fetch` replaces a file by rename, which changes the inode, so a model fetched again while its server runs restarts the server. A file overwritten in place could keep all four and isn't covered.
- A ready-made GGUF takes its tokenizer from the model it was made from, and the check after each call shows whether the two agree.
- A gated repo, such as Meta's Llama 3.1, is fetched with your own Hugging Face login (`hf auth login`), which the Hugging Face library reads. Clarity never asks for, stores or logs a token, so it holds no credentials. Without access, `fetch` stops and says how to get it.

**Shipped files stay read-only, and your files live in `local/`.** Clarity never edits `models.toml`, `profiles/`, `defaults.toml` or `server.toml`. Your own profiles go in `local/profiles/` and your own models in `local/models.toml`, which git ignores, so a `git pull` never touches them. A profile or model name that exists in both places is an error, because the name must say which file it means. Your models' lock entries are read from `local/models.lock` only; where an entry came from isn't logged, so a call's `model` is the same on either. Clarity writes into `local/`, `logs/`, `runs/`, `models/` and the Hugging Face cache, and setup also writes `vendor/llama.cpp` and the Desktop launcher ([Setup](#setup) lists everything the install writes); it appends to a log you name (`clarity replay`, `clarity mark`, `clarity note`; replay also puts the server's output next to it). A new kind of write must be visible to you when it happens.

**Every chat command is in one table,** which the terminal, `clarity chat --json` and the web interface all run. Each command returns its result as data and reports what happens while it runs as events: reply text as it streams, a model starting, and every record written to the log. So a script or another program can do anything you can do in the terminal, and see what you'd see.

**One running Clarity per project.** `chat`, `ui`, `run` and `replay` hold a lock on `local/clarity.lock` while they run; a second one stops and says which process holds it. Two would load two models, more memory than a laptop has, and could write to the same log. The operating system releases the lock however the process ends (on Windows, possibly after a short delay), so a crash never leaves it stuck. `clarity mark` and `clarity note` only append a line, so they don't take it.
- Who holds the lock is in a separate file, `local/clarity.json`, because on Windows a locked file can't be read by another process.

**A crash doesn't leave a model in memory.** llama-server runs in its own process group, so it outlives a Clarity that is killed or crashes, holding 14 GB or more. Two things prevent that:
- SIGTERM, and SIGHUP from a closed terminal, exit Clarity through its normal cleanup, which stops the server.
- While a server runs, its port, process ID and key are in `local/clarity.json`, and so are meaning search's embedder's, under `embedder`. If Clarity dies anyway (`kill -9`, a power cut), the next `chat`, `ui`, `run` or `replay` finds them there and asks that port's `/props`, with that key. Only an answer naming the same model stops it, and Clarity says so. That answer proves something on that port holds the record's key and serves the record's model, not which process it is: the process Clarity signals is the one whose ID the record holds, which Clarity trusts as part of your `local/` folder. Anything else is reported and left alone. No process list is read, so this works the same in a sandbox and on Windows. A Clarity older than v0.4.1 doesn't read `embedder` and rewrites the file when it starts, so it leaves an embedder a crash left running, with no record of it: stop that `llama-server` from Activity Monitor.
- Cost: a per-start key sits on disk while the server runs, readable only by you.

**Logs are append-only JSONL,** one file per chat conversation and one `calls.jsonl` per batch run, with a schema version. Every call writes a record, including failed and cancelled ones. Readers ignore keys they don't know, so later additions need no format change. A line cut off by a crash or a full disk stays as it was: the next write ends it and adds a `torn_line` record naming it, and Clarity says so. Until then, readers treat a last line with no line end as not yet written, so reading a log never writes to it. A line a `torn_line` names is never a record, even if it parses, so a log reads the same before and after it's mended; any other damage still stops them. `logs/` and `runs/` are private and gitignored.
- Cost: a chat keeps every call record in memory, about 4 to 5 times its size in the log. Each prompt is capped at the context size, so this grows with the number of calls: 400 calls at an 8,192-token context hold about 200 MB. A 32k context with `logprobs` on comes nearer 1 GB, and on Transformers that's in the same process as the model.

**Failure policy.** Configuration problems are errors before anything is sent. A failed check after a call is a flag on the record and a warning in the terminal; in a batch run, it stops the run.

## The Transformers backend

**It runs the same weights in-process.** It loads the official weights the GGUF was converted from, in bf16, and is given the same prompt token IDs as llama-server, so the two backends can be compared, and a call's activations can be read in PyTorch.
- Every output-affecting `GenerationConfig` field is set on every call, and the model's own generation config is replaced by an empty one at load. Otherwise Transformers fills unset fields from the model's file and then from its own defaults (`top_k` 50, for one). Only `eos_token_id` comes from the model: from its `generation_config.json`, or, if that lists none, from its tokenizer's end token, which Clarity says at start. The IDs and their source are logged and shown in `/settings`. Some models need the second: OLMo 3 base's file lists no end token, and Qwen3.5-9B ships no file. Transformers' own fallback, `config.json`, would give Qwen 248044 (`<|endoftext|>`), not its chat stop `<|im_end|>` (248046). A model with an end token in neither is an error.
- The attention implementation is set to `sdpa` explicitly, because Transformers' default falls back to `eager` without saying so.
- Some settings can't run on Transformers as written (see [Settings](reference.md#settings)). They are recorded as not applied rather than refused, so a profile still runs on both backends and the record says how they differed.
- `PYTORCH_ENABLE_MPS_FALLBACK` is refused on MPS, because it would run unsupported operations on the CPU without notice.
- PyTorch's deterministic mode is never turned on: in inference it makes nothing deterministic on MPS or CPU and can only raise errors. Its state is logged.
- **Token probabilities come from the raw scores, on Transformers first.** With `logprobs` on, `generate` also returns each step's logits, taken before any sampler, and Clarity turns them into log-probabilities after the reply is done. So the numbers say what the model itself gave each token, not what temperature or `top_k` did to it. One view is recorded, and the record names it. llama.cpp profiles refuse the setting until v0.4.0: its probabilities need a change to how it samples (`n_probs`), which must first be tested for its effect on the reply, and a reply that quietly lacks the numbers you asked for would be a silent fallback.
  - The log-softmax runs on the CPU in float32. On MPS, the same row gave slightly different results (in about the 7th significant digit) depending on how many rows were processed together; on the CPU it didn't. From that test we infer that only the logits depend on the device, and a recompute that reduces the same way gets exactly the same numbers from the same logits. Measured on SmolLM2 on CPU and MPS: the logged probabilities equal a step-by-step recompute with the cache exactly, and turning `logprobs` on doesn't change the reply.
  - Cost: the scores stay in memory until the reply is done, about 0.4 MB per token for a 100,000-token vocabulary, and the log grows by about 0.8 MB per 4,000-token reply at `logprobs = 5` (estimated from the width of the stored numbers).
- **The recompute check gives facts and numbers, not a verdict.** A notebook that recomputes an export's probabilities under other conditions gets other numbers, so `clarity_chat.recompute.check` lists each condition that differs and measures the largest gap and the changed top choices. It recomputes step by step with the cache, as generation ran, because in bf16 one pass over the whole sequence differs even under the same conditions: the sums run in another order and round differently (one 60-token SmolLM2 run, CPU, bf16: a gap of 0.139 and 2 changed choices, against 0 step by step; in another such run, 0.177 in bf16 and 0.0000145 with no changed choices in float32). It sets no threshold: what matters depends on the experiment.
- **Steering adds a pinned vector, on Transformers first.** A profile names a control-vector file (llama.cpp's format, as repeng and `clarity vector make` write it) by path and sha256. For each call, a forward hook adds the scale times `direction.N` to the output of block N at every position, and comes off when the call ends, however it ends. The vector, scale and blocks are in the call's request, so a replay applies the same ones, and a check confirms every forward pass of the call ran each steered block once. On MPS, Transformers decides to stop one step late and runs one more pass, which it then undoes, so a call can have one more pass than reply tokens; that pass is steered too.
  - The hooks run before the ones Transformers uses to record `hidden_states`, so a notebook reading activations sees the steered values.
  - The scaled vector is computed in float32 and cast once to bf16, as repeng computes it (casting first and scaling in bf16 rounds differently), then added in bf16. llama.cpp adds it in float32 to float32 hidden states: the same sums, not the same numbers. How far apart they land isn't measured.
  - Block 0 is refused, only because llama.cpp has no vector slot for block 0 and its loader refuses `direction.0`; Clarity keeps a vector usable on both. The last block can be steered, but repeng, which steers it by default, reads that block's output after the model's final normalization (Transformers' last `hidden_states` entry), so such a vector is trained on a different quantity than the one it's added to. The guide says to leave it out.
  - Steering runs on model types `llama` and `olmo3`, whose blocks Clarity has checked return a plain tensor from `model.model.layers`. Other types are refused until checked.
- **Making a vector reads the tensor steering adds to, and reports facts about the pairs.** `clarity vector make` turns a file of contrasting prompt pairs into a control vector on the Transformers backend ([Making a vector](reference.md#making-a-vector)).
  - The vector is the average difference between the two sides. Across seven behaviours on one model, one comparison found this beat directions found by PCA or by a classifier on most tasks; a classifier did better on three of them in open-ended replies (Im and Li, [arXiv 2502.02716](https://arxiv.org/abs/2502.02716)). Its sign is fixed, positive minus negative: nothing here is PCA, so no sign fix is needed.
  - It isn't scaled to length 1, so `steering_scale = 1` adds the average difference between the two sides, on any model, and each block's push stays in proportion to its own gap when `layers` widens. The cost: repeng's default method and llama.cpp's `cvector-generator` both write vectors of length 1, so the same scale on one of theirs is a different push, and the file's format can't say which kind it is. The record says `"length": "not normalized"`, and the docs label each `4.0` example as a repeng vector's.
  - A forward hook reads each block's output, the tensor `applied` adds to. Transformers' `hidden_states` would do for every block but the last, whose entry comes after the final normalization: the quantity repeng reads there, which isn't what steering adds to.
  - Each prompt is read at its last token, after the reply's opening words. With an empty opening this is persona vectors' "prompt last" ([arXiv 2507.21509](https://arxiv.org/abs/2507.21509)); that paper found the reply's average steered best, so it doesn't back this choice. With an opening, it is the opening's last token, which that paper didn't compare.
  - Every block that can be steered is made, because one pass over a prompt reads them all; so the readout shows every block and the user widens `layers` with no remake. The printed snippet applies one block, the middle one, as a starting point: one block is what several published methods ran.
  - The record is a file beside the vector, not a log record: logs hold conversations, and `local/models.lock` is the precedent for a file about something else. Its sha256 and the vector's tie the two together.
  - The readout gives each block's activation size, gap and agreement, and no rating of replies. Rating replies needs a judge, which stays out of scope ([Not in scope](#not-in-scope)).
  - Clarity reads the file with its own small reader rather than the `gguf` package: it parses the bytes it hashed, in one read, and every malformed file gets a message saying what was wrong.
- Only one chat model is ever in memory (a chat that searches by meaning also runs the embedder beside it). If a new model fails to start, the previous one is started again, so a bad `/new` or `/profile` leaves you where you were. A failed start that was the open conversation's own (the same backend, model, weights and context size), as "Start the model again", a Replay or `/new` on the same profile make after its server stopped, is the exception: the same start would fail the same way, so it isn't tried again, and the conversation stays with its model stopped, to be tried again.

## Conversations and runs

**Branches never overwrite.** `/regen`, `/edit` and `/undo` start new branches, and every turn stays in the log with its parent. A `/regen` uses the highest seed used for the message plus 1, which for replies made only by `/regen` is the first reply's seed plus k: with the same seed and settings it would only repeat a reply, and checking that is `/replay`'s job. `/regen same` reuses the seeds on purpose, under changed settings, so the change is the only difference between two replies with the same seed.

**`/compare` groups replies by their logged settings, not their requests.** Each backend logs its own request body, so two calls with the same settings can have requests with different keys. The settings table uses the same names on every backend, with the seed left out, since the seed is what differs between replies made to compare.

**Replay re-sends the logged request, not a rebuilt one.** It sends the logged token IDs and request body, so a later change to how Clarity builds requests can't change a replay. It then lists every recorded fact that differs from the original call, so a different output comes with its likely causes.
- Cost: replay can't show whether a later fix to how requests are built changes a reply; that takes a new call.
- `clarity replay`, with no conversation running, finds a call's model by its file, not only its name, so a call still replays on an entry with its file under another name. Lock entries are kept by name, so an entry you rename is fetched again under its new name first. It reports and doesn't repair: when no entry has the file or the name, it lists the call's pins and stops, and never fetches or adds an entry. In a conversation, `/replay` runs the call on the conversation's model, and refuses a call made on another model with the way out: resume the conversation it's from.

**Resume continues a conversation as it was logged.** `clarity chat --resume LOG` uses the profile's logged text and files, its resolved settings, its `/set` values and its logged context size (a `/set ctx_size`, else the conversation's size, else, for an older log, its last call's), not today's files. Then it says what differs: a changed profile file, settings today's files would resolve differently, the facts replay compares (server build, flags, machine, libraries), and whether the current reply's prompt still renders to the same token IDs with today's template and libraries. `/switch` runs that last check again for the reply it goes to. Some things can only be today's: the model's `models.toml` entry, `server.toml`'s flags other than the context size, the llama.cpp build and the libraries. Each is compared with the log and listed when it differs.
- The conversation continues where the latest `turn` or `head` record says; a message whose call never finished means the turn before it. v0.1.0 logged neither `/undo` nor a failed call's move back, so for its logs that place is a guess, and Clarity says so.
- Cost: a resumed chat keeps old values even when you'd rather use today's. `/set` or a new conversation changes them, visibly.
- A batch run's `calls.jsonl` can't be resumed: each of its calls is a conversation of its own.

**Batch runs are blind, checked first and kept apart.**
- Before any model loads, every opening is rendered against every profile. Unequal `max_tokens` stops the run, because reply length would give a setup away. The cost: all profiles in a run share one `max_tokens`.
- Seeds come from the run, starting at 42 like the default seed, so two runs with the same profiles are comparable, and `--seeds N` shows a setup's spread rather than one sample.
- Openings files have their line endings normalized, so an editor's line endings never change the token IDs.
- A server restart mid-run stops the run, so no run mixes server processes.
- Nothing goes to `logs/`, not even the server's output, so held-out openings never end up in a transcript export.
- A profile that searches documents searches each opening once and sends those parts with every seed, so seeds vary the reply, not what it was given. Two profiles can still get different parts for one opening: each counts the budget with its own tokenizer, or has its own budget. The run says so for each opening where that happened, because a rater comparing the replies would otherwise read a difference in what the model was given as a difference in the setup under test.

## Export for Inspect

**A finished run or a chat exports as Inspect logs, through `inspect_ai`'s own writer at one pinned version.** The use is browsing and comparing replies in `inspect view`, with a log any Inspect-based tool can read. Inspect's own writer keeps the format right. Inspect promises no format stability beyond its API, so the `inspect` extra pins one exact version, and an export refuses any other. A bump is its own commit and reruns the tests of what the viewer does with Clarity's logs. `inspect_ai` is imported only when an export runs.

**One log per profile.** An Inspect log names one model, and the tools built on it assume that. The model is `clarity/PROFILE`, which names no Inspect provider, so nothing re-runs it by mistake. Each opening is a sample and each seed an epoch of it, so every profile's log uses the same sample IDs, and the viewer's grid, sorted by Id, puts every profile's replies to one opening on adjacent rows.

**A chat is one log, and each reply its own sample.** A chat's replies to one message, its `/regen`s, would be epochs of one sample, but each message has its own number of replies, and the viewer reads uneven epochs as missing replies ("4 / 6 Samples"). So each reply is a sample of epoch 1, named by the message it answers and its place among that message's replies (`TURN-N`), and a message's replies sort together by Id. A run keeps its epochs, since every opening gets every seed.

**Inspect's fields hold only what is exactly true of a call; everything else is in metadata.** The generate config is left empty. No log-wide config could be true, since the seed differs per epoch. Inspect's config has no field for some of Clarity's settings: min_p, the repeat penalty and its window, the sampler order. And the ones it has mean less than they seem to: llama.cpp runs the profile's sampler order, and its penalties count only the last `repeat_last_n` tokens, the prompt included; Transformers runs a fixed order, flags `not_applied` when the profile's differs, and may not apply some settings. So a `temperature` in Inspect's config would say less than it seems to. Each sample's metadata is exactly the plain export's row for its call, plus the call's `run`. It is flat, not nested, because Inspect's summaries shorten a string past 1 KB and replace a list or object past 1 KB with "Key removed from summary"; flat, the small fields stay in them. The log's metadata is the plain export's header and, beside it, a note that Clarity, not Inspect, made the calls: the viewer folds a header with many keys, but shows a single string. The log's tags say so too, in its header and Task tab.

**Messages are slices of the prompt.** In chat mode, each message is exactly its part of `prompt_text`, with its role, so no message holds text the model didn't get. One exception: a call with no system message of its own gets one holding the text the template wrote of its own before the first message, markers included, since some templates write a whole system message there (OLMo 3's does) and the model got it. Telling that text from the first message's header needs no knowledge of each template: the header is the ending the text shares with what the template writes between a turn's end and the next message, and the BOS text comes off only if a render shows the template writes it (SmolLM2's BOS text is also its role marker, which its template writes as a marker). Other text the template adds is kept in `prompt_text` only, and the note says so. And the log asks the viewer to show its text as written (Inspect's `trust_content = False`), as Clarity's page does: rendered as Markdown, a reply's leading spaces would be dropped and a line starting with `* ` would become a bullet. The same setting shows hidden characters as markers and withholds media, which suits a page for reading what the model wrote. A text-mode prompt has no roles, so it is one user message holding the whole prompt. A sample's input is the opening's message as the model got it, in both modes, so profiles' rows for one opening show the same input unless search added parts to it.

**A stop reason is Inspect's only where it means the same.** End of sequence and a stop word are `stop`. llama-server's limit also ends a call whose context filled, so a call stopped at the limit is `max_tokens` or `model_length` by the flag Clarity logged with it. Anything else is `unknown`; the stop type itself is in the metadata.

**Marks become a score with no metric.** Every reply gets a `mark` score. Its value is the reply's labels as one string, or "unmarked", so the log's sample list can filter by it; its answer is the reply, and its explanation the reply's notes. A mark is a label, not a measurement, so the log names no scorer and no metric. `inspect score` can add a real score beside it.

**Two exports of one run read back the same.** The IDs come from the run's and calls' logged IDs, and the times are logged ones: the calls' own, and a run's start its run record's. Cost: an export replaces the file, scores added to it since included, so score again after exporting again.

**The file is private from birth.** Inspect's writer creates its temporary file with the default permissions, readable by others under the usual umask, so Clarity has it write inside a private temporary folder, makes the file readable only by you, and moves it into place.

## Attached documents

**An attachment is part of its message.** Attaching a file puts its text in a block at the start of your message, after a framing line (unless the profile sets none) that says it's reference material. The line is the profile's: changing it is changing the profile, so a chat's prompts never depend on a value set mid-chat. Each turn records the line it was sent with and where it came from. One function builds every message's content: the prompt, its message spans, the render check, resume and the export all use it, and it is built so that later sources of text can use it.
- The turn record keeps your message as you wrote it, with the attachments beside it. So a regeneration reuses them without reading the file again, `/edit` keeps them (or leaves out those you drop), and a branch brings only its own.
- A failed send puts the message and its attachments back, waiting for you to send again.
- Nothing is trimmed. A chat that outgrows its context stops at the check every call goes through, and the sentence says how many of the prompt's tokens the attached documents and their framing lines take, counted from the call's own message spans (when a template keeps those from being found, it gives each attachment's cost when it was attached, and says so). There's no way to send anyway.
- Privacy: a log and an export hold the text of the documents attached in them. The record keeps a file's name, never its path. Attachments still waiting aren't logged, so a resume drops them, except a failed message's, which come back with it.

**Extraction runs in a child process with limits.** `pypdf` has had advisories for unbounded memory use and infinite loops on crafted PDFs, and the web page's commands run on one worker thread, so a parser stuck in Clarity's own process would freeze it, Stop included. The child runs with `python -I` and an environment with nothing of Clarity's (no tokens, no paths). It gets 120 seconds, at most 1 GB of memory (its own watchdog polls every 20 ms, and on Linux `RLIMIT_AS` stops it at twice that) and 256 MB of output; files over 64 MB (67,108,864 bytes) are refused before they're read. The child runs in its own process group, so a terminal's Ctrl-C reaches Clarity, which turns it into a cancel. Reading, extracting and counting a file (below) each end, at any limit or error, in a refusal with a sentence, never a stopped session.

**Counting is bounded before anything renders the whole.** A small file can still hold a lot of text: a 7 KB PDF whose pages share one compressed stream holds 10 million characters (`tests/pdfs.py`'s `shared_stream_pdf(40, 256 * 1024)`, which `test_an_amplifying_pdf_is_checked_within_a_bound` reads). Counting a document exactly means rendering the prompt with it and tokenizing that, in Clarity's own process, and for 64 MB of text that takes minutes and gigabytes. So Clarity bounds it first. For a byte-level tokenizer with no normalizer, no token covers more text than the longest token, L bytes (computed once per tokenizer), so a prompt of B bytes takes at least B / L tokens. When that least cost is more than is free, the document doesn't fit, and the sheet and the refusal say "more than N tokens" without counting it. Otherwise it's at most about free × L bytes, and it's counted exactly. Each count checks `/cancel` first.
- The bound holds for tokenizers whose tokens decode back to the text: byte-level BPE with no normalizer, which is what the chat models Clarity ships use (SmolLM2, OLMo 3, Llama 3.1). Clarity takes it only for such a tokenizer; for any other (a normalizer can shrink text, a SentencePiece decoder drops a lone token's leading space) it counts exactly, which is correct but slower.
- A chat with no room left at all (its messages and `max_tokens` already fill the context) is refused before any count, in a plain sentence.
- Cost: a document that doesn't fit shows a lower bound, not its exact cost. Finding the start that fits still counts exactly, and none of its renders is longer than twice the answer. A document that fits is counted exactly, at up to the free context's tokens: at a 128K context one render can take many seconds and gigabytes (one encode of 16.7 MB of text with Llama 3.1's tokenizer took 11.9 s and peaked at 3.9 GB, on a busy machine; part 1's fix review measured it), so a check keeps its whole and new-chat counts for the last document and chat state, and the sheet's range changes count only the range.
- Cost: memory can overshoot by what's allocated between two polls, and Windows has no memory guard until v0.7.0 (the time limit still holds there).
- The same extractor version gives the same text from the same bytes, with one exception: HTML is read with Python's own HTML parser, which has changed between Python releases, so another Python can change its text. Each attachment logs the extractor's name and version (for HTML, the Python version too), the file's sha256 and the whole extracted text's sha256, so a change shows.

**The library keeps what search reads, and holds nothing of yours.** `clarity document add` copies a file into `local/documents/NAME/` with the text Clarity read and the parts it cut, so you can inspect what search reads. Search reads `parts.jsonl` and checks it against the build ID in the manifest; a document whose parts aren't the ones Clarity built can't be searched, and the way out is to add the file again. Adding under a name that's taken replaces that document, and Clarity says so before and after. Your file is the thing to fix: there's no rebuild from an edited `text.md`, no check command, no `--replace` flag and no "already added" rule.
- Why: each of those was a recovery path with its own sentences and buttons on every front end, for a library whose job is to let you test replies with documents in context. Exactness only needs the build ID check; the rest was workflow.
- Cost: to give a PDF's parts titles, or take text out of a document, you edit your own file and add it again; editing `text.md` changes nothing.
- The web interface adds a document only through the paperclip's **Search it**, and lists the library only in the Searching chooser. There's no page for managing documents: the library is a means to an experiment, not something to curate. Cost: no view of the library with no chat open, and no way to try a search on the page; `/documents` and `/try` do both in a terminal chat.
- Parts are cut by Markdown headings and paragraphs, up to 250 words, so a glossary's headwords title their entries; a PDF has none.

**Search is the insertion path's second producer, and its parts stay with their message.** When a chat searches documents, each message you send (or edit) is searched with the words you typed, and the best parts that fit the budget (1,500 tokens by default, the framing line and wrappers counted) go into the same block as attachments, at the start of your message or, with `placement = "end"`, after it. The parts are stored on the message's turn, so every later call sends them where they were added: earlier turns never change, so a server's prompt cache keeps working, and a regeneration reuses them from the log without searching again, even after `/search` changed. A part already in the chat on this branch isn't added again and costs nothing. An edit is a new message, so it's searched with its new text, and keeps its attachments.
- Cost: parts accumulate. A chat that asks about many subjects carries every part it found, so it fills its context sooner than one that asks about one; the stop says how many of the prompt's tokens found parts take.
- A searched document that's missing or unreadable, a Python without SQLite's FTS5, or a found part holding a control token for this model, refuses the call before anything is sent: the call is logged as failed, the message comes back, and the sentence says the way out that exists where you are, a command in the terminal and a button on the page. A control token you didn't choose would end your turn early. It's said only then, when a message finds the part, not counted in advance when you choose a document: the count cost a tokenizer pass over every part, and the refusal names the part anyway.
- "From documents" gives each part one number, its rank, and the parts left out as counts. Each part's tokens are in Details, next to where it sits in the prompt, where they add up to the spans.

**What a chat searches is part of the chat.** The profile's `search` list sets the start, and `/search` changes it for one chat, logged as a `search` record as `/set` logs a setting, so a resumed chat searches what you chose. A profile naming a document that isn't in the library doesn't start, and says which key to change, rather than starting with a gap you'd only notice in the replies. A document that goes missing later is listed as missing, and `/search` without it works.

**Word search, and its limits.** Search uses SQLite's FTS5, from the standard library: no new dependency, and 20,000 parts are searched in about half a second. A part matches if it shares any one uncommon word with your message, so a message with such a word matches every part that shares it, and only the best 8 are considered. A message of common words only ("ok, thanks") matches nothing. The words come from the message you typed, never from earlier ones or from an attachment, so a follow-up like "tell me more" finds nothing. A paraphrase that shares no word is missed; meaning search, the default, usually finds it. The stemmer and the common words are English only. The order is the same for the same text, build and SQLite version; Clarity claims no more than that across systems.

## Meaning search

**A chat's search keys are set like its settings, but stay out of the call.** `/set` takes `search_method`, `min_similarity` and `budget` as well as the sampling settings, checked as the profile's `[documents]` table checks them. They change what a message's search adds, which the message's `found` logs with each value's origin; they don't change the call. So a call's `settings` holds sampling settings only, and replay, which never searches, has nothing new to read. Cost: two places to look for what a chat used, the call for sampling and the message for search.

**A chat searches by meaning unless its profile says words.** Word search misses a paraphrase that shares no word with your message; meaning search, which finds the parts closest in meaning to the message, usually finds it. Neither finds anything for a follow-up like "tell me more". `search_method = "words"` in a profile keeps word search, and `/set search_method` switches a running chat from its next message. A batch run uses its profiles' values, so comparing the two methods over many prompts is a `clarity run` with two profiles. A resumed chat searches by its own `/set` method if it has one, else its logged profile's. If neither names one and the chat never set a method, it keeps the method of its last searched message, so a chat begun before meaning search keeps searching by words and needs no embedder.

**The model is bge-m3, on a second llama-server.** It was chosen because it reads up to 8,192 tokens and needs no query or document prefix. Cost: newer models score higher on retrieval of short passages; the vendor-reported English MTEB retrieval scores (MTEB-R) in Snowflake's model card for snowflake-arctic-embed-l-v2.0 give 0.556 for it against 0.488 for bge-m3. `clarity fetch` converts bge-m3 to a bf16 GGUF of about 1.16 GB.
- The embedder is a second llama-server, started through the same code as the chat server. It starts the first time a session needs a meaning search (a message, `/try`, a run's first search). It stops when a chat that doesn't search by meaning starts its model (a new chat or a resume), so its memory is free for the chat model, and when the session closes; the next need starts it again, and the vectors are cached. `/search`, opening, resuming, replaying and exporting never start it, and neither does a chat that searches by words.
- Its flags are constants in `documents/embedder.py`, not in `server.toml`, so a change to the chat server's flags never changes a vector; each searched message logs them. Its context, batch and ubatch are all 8,192 tokens: bge-m3's attention isn't causal, so llama.cpp needs the whole input in one ubatch, and flash attention keeps it from building the full attention matrix.
- Two servers share the GPU, and the memory check counts both ([The server](#the-server)).
- The Transformers backend has no embedder of its own: meaning search on an `hf` profile still needs the llama-server binary.
- `local/clarity.json` records the embedder as it records the chat server, so the next start stops one a crash left. An older Clarity doesn't read that key, and leaves such an embedder running.

**The vectors are a cache, keyed by what's known to change them.** The setup is the sha256 of the embedder's facts: the model's name, the GGUF's sha256, the tokenizer's repo and revision, the `tokenizers` version, the llama.cpp commit, the flag table, the input rule, the device and the machine (OS version and build, chip). A document's vectors file is keyed by its build ID and the setup. It's built before the first search that needs it, and Clarity says so first, naming where it saves. It's read as untrusted: its size, every value and every vector's length are checked, and its sha256 is logged with the message.
- The embedder won't start with a `GGML_*` or `LLAMA_*` variable inherited from your environment, or on a llama.cpp checkout with uncommitted changes, since the setup records neither.
- Cost: an OS update changes the setup, so every document's vectors are built again. And a vector can still change with no recorded fact changing (another compiler, say).

**Scoring is exact, and the minimum decides what matches.** The similarity of two vectors of length 1 is their dot product, from -1 to 1. Clarity computes it in plain Python: each product of two float32 values is exact in float64, and `math.fsum` rounds the sum once. The Python docs make that depend on IEEE 754 double arithmetic with round-half-even and no extended-precision addition, which holds on x86-64 (SSE2) and arm64, the platforms CI checks the golden order on; there, the same vectors give the same bits. Parts at or above `min_similarity` match, highest first, then by document name and part number; the best 8 are considered and added until the budget is full, as for word search.
- The default minimum, 0.5, was measured on made-up glossary, prose and reference-list text as the lowest value that leaves out "ok, thanks" and "hi". A true match can score just under it: in the measurement, one paraphrase of nine scored 0.494. So `/try` says how close the best part came when nothing matched.
- A message or a part past 8,192 tokens is refused, never cut.

**What meaning search claims, and no more.** Replay, regeneration and resume are exact because they never search: the parts are stored with the message. On one machine, OS and build, with the same setup, the same message and documents give the same parts, byte for byte. Across machines, OS versions or builds, vectors can differ; the setup changes, and the vectors are built again. It's tested on Apple silicon (Metal) only. Its flags put every layer on the GPU, and the placement check refuses a start whose weights land on the CPU, so where llama.cpp finds no GPU, meaning search is refused and `search_method = "words"` is the way out.

## Determinism and replay

**The same call on the same machine and build gives the same output,** at any temperature, because the seed is always fixed. Live tests check this back to back, after a longer call in between, and after a server restart, on SmolLM2 and OLMo 3. The Transformers backend passes the same checks (back to back and after a reload) on MPS for SmolLM2 and OLMo 3 Instruct, and on the CPU for SmolLM2. It holds because Clarity removes what usually varies: one request at a time, no prompt cache, and fixed batch sizes, so every GPU kernel sees the same shapes every time.

**Some changes can change the output, and that's expected.** Floating-point sums depend on their order, and when the top tokens are nearly tied, one flipped token changes the rest of the reply. The order changes with:
- the llama.cpp build, batch or micro-batch size, flash attention or KV cache type
- the GPU family, or the macOS version, since Metal compiles llama.cpp's GPU kernels when the server starts
- some `GGML_*` environment variables, and the GGUF itself

Clarity logs all of these, and replay lists the ones that differ.

**Warnings are for things you can act on.**
- Per call: a failed check, a nearly full context, or control-token text in your message.
- Per server start: a `llama-server` binary built from another commit than the pinned one (a checkout at another commit is refused instead), uncommitted changes in the llama.cpp checkout, or inherited `GGML_*` or `LLAMA_*` variables (or `PYTORCH_*` and `TORCH_*` on the Transformers backend), whose values are logged unless the name looks like a secret.

There is no general "results may vary" notice. Replay flags the one case that needs attention: output that differs although nothing that could explain it changed.

**Not attempted:** identical output across machines, builds or backends; llama.cpp's experimental batch-invariant kernels, which fix a variation Clarity's single-slot setup doesn't have; and a determinism guarantee for the Transformers backend on Apple GPUs, which PyTorch doesn't provide. The live tests check that case instead.

## The web layer

**The page is a view of the same command table.** Every action and every read goes through the commands the terminal and `--json` use, so the web interface can't do or show something a script can't. One worker thread owns the session: commands queue and run in order, as with `--json`; the ones the table lets run during another (`state`, `cancel`, `chats`, `profiles`, and `settings` and `prompt` during a reply) don't wait.

**The server trusts nothing but its own page.** It listens on `127.0.0.1` only and checks the exact Host on every request, which stops DNS rebinding. The threats it's built against are a page on another site, or on another `127.0.0.1` port, in the same browser; a rebinding page; and another user on the same computer.
- **A secret per start, in the link's fragment, sent as a header.** The fragment never reaches a server, a log or a `Referer`. A page from another origin can't read it, and can't send an `Authorization` header to `127.0.0.1` without a CORS preflight, which the server refuses, so a cross-site request fails before anything else is read. A cookie would be simpler for the page but worse: browsers send it to every port on `127.0.0.1`, so any local web page could use it.
- **Fetch metadata and Origin** are checked as well, as a second layer, and every response carries a strict content security policy (scripts, styles and fonts from the page's own origin only; no framing).
- **Untrusted text is escaped.** Replies, notes, labels, titles, descriptions and error sentences go into the page through autoescaped templates or as plain text; the page's script has one way to put server HTML into the page and none to build HTML from text, and the content security policy's Trusted Types make the browser refuse any other way, where it supports them.
- **The port is Clarity's before the link exists.** `clarity ui` binds and listens on it before printing or opening the link, so no other program can take the port in between and receive the secret.
- **Its limits:** while Clarity runs, the secret is in the terminal's output (and in any file that output is sent to), in `local/clarity-open.html` until the page it opens connects (a tab already open can't use up the one Enter writes), in the tab's session storage, and in the browser's stored session and possibly its history; anyone who can read those can use it. Another user on the same computer can reach the port and tie it up, but can't read the secret. For now Clarity assumes one user per computer. After Clarity stops, any program can listen on its port. A tab left open stops when `/state` comes from another start, so it neither draws nor loads what that program sends. A tab you reload, or the address typed again, does load that program's page, which shares the address's browser storage and can register a service worker there; that worker could read the secret in the link of Clarity's next start. Close Clarity's tab when you stop Clarity.

**The page's fonts ship with Clarity, unmodified.** Rasa (Rosetta) for what was said, IBM Plex Sans for what you can do and IBM Plex Mono for what is exact, so the page looks the same on every computer and loads nothing from the network. They're the publishers' own files, under the SIL Open Font License 1.1, each family with its licence beside it in `web_static/fonts/`. IBM reserves the name "Plex", which a modified font couldn't keep, so neither family is subset or converted: Rasa reserves no name, but it ships unmodified too, for one rule (as TTF, as Rosetta publishes it). Only the weights the page uses are included.

## Setup

**Clarity lives in a git clone.** The install command clones Clarity at the release's tag into `~/Clarity`. Clarity finds its folder by looking upwards for `defaults.toml` and `server.toml`, and logs its own commit, and whether it has changes, with every call. A clone keeps both working as they do in a developer's checkout; a wheel would have neither. Updating an install isn't supported yet: run again, the install command says when `~/Clarity` is at another release, and leaves it as it is. Getting started gives the steps by hand for a release that moves neither the pin nor a conversion. A later release can pin another llama.cpp commit, and setup doesn't move a `vendor/llama.cpp` at another commit; it can also convert a shipped model again, while the older entry in `local/models.lock` stays in force, since its pins still match. An update path has to handle both, so it gets its own release.

**llama-server is built from source on your Mac.** Setup fetches llama.cpp's source at the commit in `server.toml` and builds `llama-server` with Getting started's two lines. The source is needed anyway, since bge-m3's conversion runs llama.cpp's converter from it, and Apple's command line tools bring git and the compiler together. So a prebuilt binary would save only cmake and a few minutes, at the cost of trusting a binary built on another machine. A prebuilt is the right path where a compiler is hard to get, as on Windows.
- The build's environment is cleared: cmake gets only `PATH`, `HOME`, `TMPDIR` and `LANG`, so variables such as `CC`, `CFLAGS`, `CMAKE_*`, `GGML_*`, `LLAMA_*` and `SDKROOT` can't change the build unseen. Setup names the ones it leaves out. `PATH` stays because cmake finds `cc`, `make`, `git` and `xcrun` through it. The cost: `PATH` still chooses the compiler, and llama.cpp's build uses a `ccache` it finds there.
- Setup builds only into a `build/` folder it made (none yet, an empty one, or one holding `clarity-build.log`), and fetches and builds only in a folder it reaches without a link: not through `vendor/llama.cpp` or `build/` as a link, nor through a link on the way, such as `vendor/` itself, which would put the work outside Clarity's folder. A `vendor/llama.cpp`, or a `build/` in it, that setup didn't make may be your own work, so setup stops and leaves it alone. So the options cmake caches in `build/CMakeCache.txt` are ones setup's own cleared build set, unless you configure that folder yourself.

**Replay compares how llama-server was built,** not only its commit. llama-server logs a build line at start (its commit, compiler and target) and a `system_info` line (its backends and CPU features); replay reads both from the call's logged start, so two builds of one commit made with another compiler, for another target or with other CPU features are told apart, in older logs too, whose start holds these lines. What these lines can't show: the build type (beyond a `(debug)` tag on a debug build), `CMAKE_C_FLAGS` and the other options cmake cached. Two builds that differ only in those look the same to replay; setup's cleared environment and its own build folder keep those options the same from one setup to the next.

**Setup needs 16 GB of memory.** At the first model's gate, on a 32 GB Mac, Gemma 4 E4B beside bge-m3 used about 4.4 GB on the GPU and about 3.2 GB of host memory, mostly file pages macOS can drop. That leaves room in 16 GB for Clarity's own process and macOS. A 16 GB Mac's Metal limit, which Clarity's memory check counts GPU buffers against, wasn't measured, so the floor rests on these figures, not on a run at 16 GB.

**Setup's fetches are ordinary fetches.** They record each model in `local/models.lock`, whose entry wins over the shipped lock's ([Models and files](#models-and-files)), so a fetch never changes a tracked file in `~/Clarity`.

**Every download is pinned.**

| What | From | Pinned by |
|---|---|---|
| `install.sh` and Clarity | GitHub, at the release's tag | the tag |
| uv's installer | `astral.sh`, at the version in `install.sh` | a sha256 in `install.sh`, checked before it runs; an installer that doesn't match is deleted unrun |
| uv | GitHub, by uv's installer | the sha256 of each platform's archive, written into the installer (which `install.sh` pins by its own sha256), checked with `sha256sum` before the archive is unpacked. The installer skips the check if it finds no `sha256sum`, so `install.sh` adds `/usr/sbin:/sbin` (where macOS keeps it) to the end of the installer's `PATH`, and refuses before downloading the installer if there's still none |
| Python 3.13 | GitHub (python-build-standalone), by uv | uv's own checks, at uv's version. Clarity's `.venv` may use another Python 3.13 that uv finds (Homebrew's, conda's); the converter's environment uses only one uv installed, and uv downloads it if it has none |
| Clarity's packages and `cmake` | PyPI | the hashes in `uv.lock`: the install and the launcher run `uv sync --locked` and `uv run --locked`, which stop when `uv.lock` doesn't match `pyproject.toml`, and leave out the dev group, which only the tests use. A `uv run` typed from a hint or the docs installs the dev group and doesn't check the lock: on a tree whose two files disagree, it rewrites `uv.lock`, the launcher's check then passes, and later conversations log `client.dirty` as true; `pyproject.toml` requires a uv (0.11 or later, before 1.0) that builds Clarity with its own build backend. Out of that range, uv would fetch a compatible `uv_build` from the index, which `uv.lock` doesn't pin: it doesn't lock build dependencies |
| llama.cpp's source | GitHub, `ggml-org/llama.cpp` | the full commit hash in `server.toml`, which git checks every object against; the built `llama-server --version` must report it |
| The converter's environment | PyPI | every package's hashes in `converter-requirements.txt`, wheels only |
| Gemma 4 E4B | Hugging Face, `ggml-org` | the revision and sha256 in `models.toml`, checked before the file is recorded or used |
| Gemma 4's tokenizer and chat template | Hugging Face, `google` | the revision in `models.toml` |
| bge-m3 | Hugging Face, `BAAI` | the revision, and the weights' sha256, checked before the converter loads them |

**What the install writes, and where.**
- In `~/Clarity`: Clarity, its `.venv`, `vendor/llama.cpp` and its build (the build's output in `vendor/llama.cpp/build/clarity-build.log`), `models/` (with the converter's environment in `models/.converter`) and `local/models.lock`.
- By uv's installer: `uv`, `uvx`, `env` and `env.fish` in `~/.local/bin`; by default, a line that adds that folder to `PATH` in `~/.profile`, in `~/.bashrc`, `~/.bash_profile` and `~/.bash_login` if they exist, in one zsh file (`~/.zshrc` by default) and in a file in fish's `conf.d`; and `~/.config/uv/uv-receipt.json`.
- By uv: its cache, `~/.cache/uv` (`uv` under `XDG_CACHE_HOME`, if that's set), and the Python it installs, in `~/.local/share/uv/python`.
- By setup: the Hugging Face cache, `~/.cache/huggingface` unless `HF_HOME`, `HF_HUB_CACHE`, `HUGGINGFACE_HUB_CACHE` or `XDG_CACHE_HOME` moves it, and the launcher, `~/Desktop/Clarity.command`.
- Temporary files: uv's installer, in `$TMPDIR` while it's checked, removed however the install ends; and what the commands it runs put in `/tmp`, since they don't get `TMPDIR`.

**What the install command passes on.** uv's installer and git get only `HOME` and `PATH` (`env -i`), so nothing else in your environment changes what they do. uv and Clarity also get `HF_HOME`, `HF_HUB_CACHE`, `HUGGINGFACE_HUB_CACHE` and `XDG_CACHE_HOME`, each only if it's set, even to an empty value: the launcher runs Clarity from your login shell, so the install must put the models where that shell's variables say. `XDG_CACHE_HOME` also moves uv's cache, as your own `uv` runs do. git also runs with its global and system config off, and never asks for a password. The checks before them, and the download of uv's installer, run in your environment. The cost: proxy settings such as `HTTPS_PROXY` don't reach them, so behind a proxy, install by hand.

## Not in scope

Left out from the start: tools or agents; metrics or LLM judges; multi-user features; an Ollama backend; llama-server's router mode; MLflow export.

Also left out:
- Running two chat models side by side. Two 7B models in bf16 need about 29 GB, more than a 32 GB laptop can spare.
- Speculative decoding, LoRA and llama.cpp's control vectors, which `server.toml` refuses. Steering runs on the Transformers backend.
- Live tests on Windows, and on Linux beyond one CI job. Offline CI covers all three systems, and CI runs the SmolLM2 live tier on a Linux CPU build; every other live test has run on macOS (Metal) only.
